Introduction

I interned at The Fine Arc, working mostly on their game Cthulhu's Reach: Devil Reef, an action roguelike co-op multiplayer game, loosely based on H. P. Lovecraft's novel The Shadow Over Innsmouth. We worked in Unity 2022, and the team consisted of me, Mimi Olsin(game design intern), Per Fransson, and Daniel Olofsson, my two mentors.

During my internship, I worked in multiple parts of the project, from UI and systems to gameplay and doing some design work. Early on, when we started the internship Mimi and I started with testing the game, and was tasked with finding improvement opportunities and problematic areas of the game. After testing, we concluded that some of the systems needed to be redesigned before release, mostly because they were not fun in their current state. The curse system, the incantations system, and the room-to-room combat needed to be redesigned and reworked. We also found lacking content that was needed to make the experience stay interesting.

Improving systems

We had a problematic bug where damage effects were carried over between levels. The cause of the bug was active coroutines. So the naive solution was to stop the active coroutines, stopping the damage tick, but another problem arose regarding cleanup. When stopping a coroutine outside of the coroutine, it cannot guarantee that it will reach the end of the function, where our cleanup function is. The solution to the problem was to make a cleanup system for the damage effects.

It works by caching the starting coroutine with an effect ID inside a dictionary so it can be accessed later. When an effect needs to be removed, an ID of the effect is needed, and a function injection of the cleanup function. The remove function stops the coroutine and removes the reference to the function, and then later calls the cleanup injected function. This fixes the cleanup problem of stopping a coroutine when it is active.

Enemy logic system

Early on in the internship, it was planned to have more enemies to improve the experience of the game, both to have more enemies to fight and to teach the player about up-and-coming bosses and some of their attacks. When working on making enemies, I found it hard-coded and hard to modify behavior in an effective way. Behaviors needed to be reimplemented when there were small deviations or changes that one enemy needed but not the other. After voicing my opinion about this problem, I got tasked with implementing a system that made it easy to modify enemy behavior and make it reusable.

After pondering on this problem for about 3-4 days and three rewrites, I finally came up with a solution to the problem. The new and improved enemy behavior system works by first implementing a data class that will hold and update all necessary data that it holds; for example, updating whether the enemy sees the player and where it wants to walk. Afterwards, an action class needs to be implemented; it will make actions based on the data class, for example, attacking the player when they are close enough. When the behavior wants to be used, the enemy logic script implements the data and the action class, and uses both of the classes updated inside of its own update method.

The positives of this system are that it makes it easy to swap behavior from one to another; the implementer only needs to change the classes that they want to use and run their update method. After implementing a behavior, it gets stored as a library with other behaviors that can be reused, so the base implementation only has to be done once. The system makes it easier to make more enemies, especially when they have similar behaviors to other enemies but they use a different attack or different movement.

Some of the problems with this system are that each behavior needs to be implemented in code, so it’s not friendly to people who don't have programming knowledge, and it’s not intuitive compared to behavior trees that are more visualisable.

Performance

I was tasked with fixing a performance spike that occurred when walking into a room with an enemy encounter for the first time. I investigated the problem with the help of Unity's profiler tool to see where the performance spike happens. There were three notable performance hogs that happened at the same time. The first and most performance-intensive was an audio file that was being opened and loaded into the game. This was weird because we believed we had “Preload Audio Data“ and “Load In Background" set to active on all the audio files, so most files should already be loaded. After hunting down the audio file, both “Preload Audio Data“ and “Load In Background" were deactivated, meaning when the audio played, it got loaded from file at runtime, something that is very performance intensive and is noticeable when it happens.

The second performance problem was because of setting a text element. When walking into an enemy event room, it shows a header label that can have different text, but when it happens, there is a big spike in garbage collection. Setting text normally is not performance intensive, but for some reason this specific label was expensive. After some digging, I found that the spike was caused by a canvas group's alpha being changed, something that was done to make a fade in/out effect on the label. We didn't want to remove the implementation and needed a different solution. After googling the problem and reading a lot of forums on how other people had solved similar problems, I came down to a solution. The fix was to force a mesh update with all possible text alternatives on the label; this stores a mesh version of all the text options, so when the label is used, it doesn't need to generate a new mesh for the text.

The third performance problem was caused by spawning(instantiating) new VFX players. The solution to this was to pool all repeating effects in the game.

After all the fixes were added, the performance spike was gone, and the performance of the game improved.

Poolhandeling

The game was in need of a pooling system that could handle most instantiated items and could be easily implemented. For ease of access, I made the pool a manager, so it functions as a singleton that any class can access. I use an interface to tag, and so a class implements all necessary variables and functions to work with the pool manager. The pool manager holds queues that are individual to each unique item, and to access an item from a queue, the caller needs a data key in the form of the interface. When warming up a pool, an instantiated object is needed that acts as the original item, which gets cloned up to a fixed amount. Each spawned item sets its interface variables when cloned. When an item is needed or needs to be put back into the pool, the data key needs to be given to the pool manager to get/return an item. The pool manager can distinguish between different items, and which pool an item belongs to is determined by checking that the incoming key has the same class type and shares the same game object ID, which is a hash code.

The hash code is needed to distinguish between two items that have the same base class but are two different prefabs.

This pool manager is generic and can handle most objects, and it fixes the need to spawn multiple objects over and over again, and objects can be reused after returning them to the pool.

    public virtual void WarmupPool(GameObject rootObject, IPoolObject poolObject, int amount)
    {
        bool poolExists = false;
        foreach (PoolData poolData in objectPool)
        {
            if (poolData.IsRightPool(poolObject)) { poolExists = true; break; }
        }
        if (poolExists) return;

        poolObject.InitializeObjectData(rootObject, objectPool.Count);
        bool isUiObject = poolObject.GetGameObject.GetComponent<RectTransform>() != null;
        if (isUiObject && (poolObject.GetGameObject.transform.parent == null || poolObject.GetGameObject.transform.parent != uiPooledObjectParent))
        {
            poolObject.GetGameObject.transform.SetParent(uiPooledObjectParent);
        }
        else if (poolObject.GetGameObject.transform.parent == null || poolObject.GetGameObject.transform.parent != pooledObjectParent)
        {
            poolObject.GetGameObject.transform.SetParent(pooledObjectParent);
        }
        
        PoolData tmpPoolData = new(poolObject.GetPoolType);
        tmpPoolData.InitializePool(objectPool.Count, poolObject, amount, isUiObject, poolObject.GetGameObject.transform.parent);
        poolObject.GetGameObject.SetActive(false);
        objectPool.Add(tmpPoolData);
    }

    public virtual IPoolObject GetFromQueue(IPoolObject poolObject, int amount = 3)
    {
        if (poolObject.PoolID >= objectPool.Count || poolObject.PoolID < 0)
        {
            WarmupPool(poolObject.GetGameObject, poolObject, amount);
        }

        if (!ValidateObjectPoolData(poolObject)) return null;

        if (objectPool[poolObject.PoolID].Pool.Count == 0)
        {
            objectPool[poolObject.PoolID].PopulatePool(poolObject.PoolID, poolObject, amount, pooledObjectParent);
        }

        IPoolObject tmpPoolObject = objectPool[poolObject.PoolID].Pool.Dequeue();
        tmpPoolObject.GetGameObject.SetActive(true);
        return tmpPoolObject;
    }

    public virtual void AddToQueue(IPoolObject poolObject)
    {
        if (poolObject.PoolID >= objectPool.Count || poolObject.PoolID < 0)
        {
            WarmupPool(poolObject.GetGameObject, poolObject, 5);
        }

        if (!ValidateObjectPoolData(poolObject)) return;

        poolObject.GetGameObject.SetActive(false);
        if (objectPool[poolObject.PoolID].isUiPool && (poolObject.GetGameObject.transform.parent == null || poolObject.GetGameObject.transform.parent != uiPooledObjectParent))
        {
            poolObject.GetGameObject.transform.SetParent(uiPooledObjectParent);
        }
        else if (poolObject.GetGameObject.transform.parent == null || poolObject.GetGameObject.transform.parent != pooledObjectParent)
        {
            poolObject.GetGameObject.transform.SetParent(pooledObjectParent);
        }
        objectPool[poolObject.PoolID].Pool.Enqueue(poolObject);

During my internship, I was able to learn a lot, both improving my programming ability and what an indie studio looks like and how they work.
